## Context

See `proposal.md` - Why. `document.pages: EPPProjectPage[]` and `ui.activePageId`/`ui.setActivePageId` already exist (`src/store/documentSlice.ts`, `src/store/uiSlice.ts`) — `setActivePageId` already resets `ui.selectedElementIds` correctly for the newly active page (`computeDefaultSelection`), and every component that reads the active page already falls back defensively to `document.pages[0]` when `activePageId` doesn't resolve to an existing page (`state.document.pages.find(...) ?? state.document.pages[0]`, repeated in `PageSetupPanel`, `LayoutTreePanel`, `ImageLibraryPanel`, `PropertiesPanel`, `SaveTemplateDialog`, `SelectionPanel`). That fallback already makes undo-of-add-page safe for free: the `document` slice (including `pages`) is tracked by `zundo`, `ui.activePageId` is not (per `undo-redo` spec's "History Scoped to the Document Slice Only") — so undoing an "add page" removes it from `document.pages` while `ui.activePageId` may still point at the now-gone id for one render, and the existing fallback catches it.

`createDefaultPage` (`documentSlice.ts`) already produces exactly the shape a new page needs (default `pageConfig`, blank single-`imageSlot` `rootNode`, empty `assignments`) — `addPage` reuses it rather than duplicating the default-page shape.

`isSimpleModeCompatible` (`@epp/layout-engine`) already exists and is pure/unchanged; this change only adds a new call site (page-switch time) alongside its existing use in `App.tsx` for disabling the Simple-mode button.

## Goals / Non-Goals

**Goals:**
- Make `document.pages` actually growable/shrinkable/navigable from the UI.
- Keep the Simple/Nested mode honest per page automatically, without persisting a new per-page preference.

**Non-Goals:**
- Page reordering (explicitly out of scope per the proposal).
- Page thumbnails in the switcher (explicitly out of scope — `useLayoutResolution` only resolves the active page today; thumbnails would mean resolving every page's layout just to render a switcher, a much bigger change).
- Any change to `undo-redo`'s spec. Page add/remove already falls within the `document` slice, and the existing "Editing the layout tree creates an undo step" scenario (`undo-redo/spec.md`) already generically covers "a document-level property change" — page array mutations don't need a new, narrower restatement of the same rule.
- Persisting the layout mode anywhere (schema Option C from the explore conversation) — deliberately rejected in favor of deriving it live from page structure (Option A).

## Decisions

- **`addPage`/`removePage` are composed at the top-level store (`store/index.ts`), not inside `documentSlice.ts`.** `documentSlice.ts` only ever touches `DocumentState { pages }` — it has no access to `ui` today (every existing action takes `pageId` as a parameter rather than reading `ui.activePageId` itself), and adding/removing a page needs to also change `ui.activePageId` (and, per the new requirement, `ui.layoutMode`). `startNewProject` already establishes this exact pattern: a cross-slice action defined directly in the `create()` call in `store/index.ts` rather than inside one slice. `addPage` reuses `createDefaultPage` for the new page's shape; `removePage` is a plain array filter.
- **Layout mode re-derivation logic lives in one exported pure function (`computeActivePageUi` in `uiSlice.ts`), called inline — not by having `addPage`/`removePage` call the `setActivePageId` action.** Original plan was for `addPage`/`removePage` to call `get().setActivePageId(...)` as a second step (reuse the action, not just its logic). Verification (task 5.3) caught that this produces **two** undo steps for what should be one atomic action: this app's `zundo` config has no custom `equality`/`diff`, and — per `zundo`'s source (`node_modules/zundo/dist/index.js`) — its wrapped `setState` pushes a new `pastStates` entry on **every** `set()` call while tracking is on, regardless of whether the tracked (`partialize`d) slice actually changed in that particular call. `addPage`'s own `set()` (appending the page) and `setActivePageId`'s `set()` (activating it) are two separate calls, so two entries got pushed — the first Undo only unwound the second, no-op-looking entry, silently absorbing one press before anything visible happened. Fixed by extracting `setActivePageId`'s logic into an exported pure function, `computeActivePageUi(currentUi, activePageId, nextPage) => UiState`, and having `addPage`/`removePage` fold its result into their *own single* `set()` call alongside the `document` change — `setActivePageId` itself now just calls the same pure function. One `set()` call per logical action, one undo step. (Ruled out `pauseHistory()`/`resumeHistory()` — the pattern used for drag-gesture batching — because pausing spans *zero* `set()` calls outside the pause window here; nothing would ever get pushed to `pastStates` for the action at all, which is correct for a gesture with a real pre-gesture state already on the stack, but wrong for guaranteeing the pre-action state itself gets recorded.)
- **Removing the active page's neighbor-selection uses index math, not "always go to page 0".** Per the spec: the page that shifts into the removed page's old index, or the previous page if it was last. This matches common tab-closing UX (closing a middle tab focuses the tab that slides into its place) rather than always dumping the user back at the start of the document.
- **Switcher UI: text + prev/next buttons, not a dropdown or tab strip.** Matches the proposal's explicit choice and the app's existing minimal-chrome pattern (`electron-shell` spec already forbids `View`/`Window` menu groups) — same visual weight as the existing Undo/Redo-turned-menu-items and Simple/Nested toggle buttons already in `App.tsx`'s header.
- **No confirmation dialog for "Remove Page."** Unlike "New Project"/"Open Project" (which discard the *entire* document and get a `ConfirmDialog`), removing one page is already undoable via the existing document-slice undo history — the existing precedent in this codebase reserves confirmation dialogs for actions undo can't reach (history-clearing resets), not for actions undo already covers.

## Risks / Trade-offs

- [Layout mode "flickers" between Simple and Nested as the user pages through a document with mixed page structures] → Accepted; this is the explicit, chosen trade-off of deriving the mode live per page (Option A) instead of persisting a per-page or global preference — flagged and picked deliberately in the explore conversation over the alternatives that would avoid it.
- [No thumbnails means the switcher gives no visual hint of *what* is on a neighboring page before navigating to it] → Accepted as an explicit non-goal for this iteration; the text "Page N of M" is enough to navigate, and thumbnails are a natural, separable follow-up once `useLayoutResolution` (or a lighter-weight variant) can resolve more than the active page.
