## Context

`ImageAsset.thumbnailDataUrl` is produced exactly once, in `electron/main/ipc/fs.handlers.ts`'s `decodeAndThumbnail(filePath)`: `nativeImage.createFromPath(filePath)`, then `.resize({ width, height })` down to a size whose longer edge is at most `MAX_THUMBNAIL_EDGE_PX = 240`, then `.toDataURL()`. Every caller of this — `createImageAssetFromPath` (image import) and `regenerateImageAsset` (project open / relink) — produces the same 240px-capped bitmap, and it is the *only* bitmap `ImageAsset` ever carries. Both `PageStage.tsx`/`FreeformElement.tsx` (editor) and `PreviewStage.tsx` (preview) ultimately render an image via the shared `SlotImage` component (`src/components/canvas/SlotImage.tsx`), whose `<img src>` is unconditionally `asset.thumbnailDataUrl` today.

This 240px cap is itself the correct, intentional, already-archived behavior of `project-persistence`'s "Thumbnail is downscaled to a bounded edge" requirement — nothing about that ingestion contract is wrong or being changed here. The bug is downstream: no other, higher-resolution image source was ever built, so every rendering surface — including print-preview, whose entire purpose is showing the user what will actually print — is stuck with a thumbnail sized for a 144px Image Library card.

`SlotImage` already computes the exact CSS box an image renders into via `computeImageRenderRectMm` (`src/lib/imageDisplay.ts`), given `widthMm`/`heightMm`, `scalingRule`, `specificSizeMm`, and `rotationDeg` — this returns the pre-rotation working size in mm, aspect-ratio-correct for `fitInParent`/`specificSize`, and exactly the slot's own box for `envelopeParent`/`stretch` (which rely on CSS `object-fit` to crop/stretch the *source* bitmap, not a pre-cropped one). `src/lib/units.ts`'s `mmToPx(mm, zoomLevel, screenDpi)` already accepts an arbitrary DPI (default 96, screen-oriented) — passing the page's own `pageConfig.dpi` (e.g. 300) instead converts an mm size to the pixel size that size would actually occupy when printed.

## Goals / Non-Goals

**Goals:**
- Print-preview shows every placed image at (up to) real print resolution, computed from what `SlotImage` already knows about that image's rendered size and the page's own DPI.
- No change to the editor canvas, to `computeImageRenderRectMm`/`computeImageDisplayRectMm`, or to the `project-persistence` thumbnail contract.
- The new decode path never distorts the image — it must feed `SlotImage`'s existing CSS/`object-fit` machinery a properly-aspect-ratioed bitmap, the same shape contract `thumbnailDataUrl` already satisfies today.

**Non-Goals:**
- Not fixing the editor canvas's own use of the 240px thumbnail — explicitly out of scope per the user's request; it remains a known, separate gap.
- Not building a persistent on-disk image cache, a background pre-decode queue, or any eviction policy for the in-memory decode cache — a session-lifetime `Map` is sufficient for a first version (see Risks).
- Not changing how PDF export/printing (both still unimplemented) will eventually source image data — this change only fixes on-screen preview; a future `pdf-export`/`printing` capability can reuse the same `images.decodeAtSize` primitive this change introduces, but wiring that up is not part of this change.

## Decisions

### New `images.decodeAtSize` channel returns an aspect-preserving "cover" decode, not an exact-size resize
Given a minimum required width/height in px, Main decodes the source at the *smallest* size that still has both dimensions ≥ the requested minimum, preserving the source's native aspect ratio (uniform scale factor `max(minWidthPx / nativeWidthPx, minHeightPx / nativeHeightPx)`, clamped to never exceed 1 — never upscale past native resolution). This mirrors `computeThumbnailSize`'s existing shape (`electron/main/ipc/fs.handlers.ts`) but inverted: that function finds the largest size *not exceeding* a max edge; this one finds the smallest size *not falling below* a minimum in both axes. Add it as a new pure, testable helper (e.g. `computeCoverDecodeSize`) in `electron/main/ipc/fs.helpers.ts`, alongside a new Electron-dependent `decodeImageAtSize(filePath, minWidthPx, minHeightPx)` in `fs.handlers.ts` that calls it (mirrors `decodeAndThumbnail`'s existing shape).

*Alternative considered*: resize directly to the exact target width/height computed from the render rect (i.e. `image.resize({ width: targetWidthPx, height: targetHeightPx })`, a non-uniform resize). Rejected — for `envelopeParent`/`stretch`, the render rect's width/height *is* the full slot box, which routinely has a different aspect ratio than the source image; `SlotImage` relies on CSS `object-fit: cover`/`fill` to crop/stretch the source bitmap itself at render time. Feeding it an already non-uniformly-resized (distorted) source would double-process the image incorrectly — `cover` would crop an already-warped image, `fill` would stretch a bitmap that's already the wrong shape. A uniform, aspect-preserving "cover" decode is the only version that composes correctly with the existing CSS-driven crop/fit logic, for every scaling rule.

### Target size computed from `computeImageRenderRectMm`, converted via the page's own DPI
For each placed image in `PreviewStage`, compute `renderRect = computeImageRenderRectMm(asset, box, scalingRule, specificSizeMm, rotationDeg)` (already done identically inside `SlotImage` itself — see below), then `minWidthPx = mmToPx(renderRect.widthMm, 1, page.pageConfig.dpi)`, `minHeightPx = mmToPx(renderRect.heightMm, 1, page.pageConfig.dpi)`. This is exactly "the pixel size this image will actually occupy when printed at the page's configured DPI" — precisely what the new print-preview scenario requires, and reuses `mmToPx`'s existing (already-present, currently screen-DPI-defaulted) DPI parameter rather than inventing new math.

### `SlotImage` gains an optional `srcOverride` prop; a new hook drives it from `PreviewStage`
Add `srcOverride?: string` to `SlotImageProps`; when present, `<img src>` uses it instead of `asset.thumbnailDataUrl` (every other prop and all geometry math is unchanged — aspect ratio for layout purposes still comes from `asset.widthPx`/`heightPx`, never from which bitmap is actually displayed). Editor callers (`PageStage.tsx`, `FreeformElement.tsx`) don't pass it, so their behavior is untouched.

A new hook, e.g. `usePrintResolutionSrc(asset: ImageAsset, widthMm: number, heightMm: number, dpi: number): string | undefined` (new file, e.g. `src/hooks/usePrintResolutionSrc.ts`), owns: computing the target px size, checking a module-level `Map<string, string>` cache keyed by `` `${asset.storedPath}::${minWidthPx}x${minHeightPx}` ``, returning the cached value immediately if present, and otherwise kicking off `getEppApi().images.decodeAtSize(...)` in a `useEffect`, storing the result in the cache and local state once it resolves (returns `undefined` until then, so callers fall back to `asset.thumbnailDataUrl` — the progressive-loading behavior the new spec scenario requires).

Because React hooks can't be called inside a `.map()` callback, `PreviewStage.tsx`'s inline per-image JSX (both the `imageSlot` loop and the `freeformCanvas` element loop) is extracted into two small named components (e.g. `PreviewImageSlot`, `PreviewFreeformImage`) that each call the hook once. This mirrors the existing precedent in this codebase: `FreeformElementView` is already its own component for exactly this reason (used inside `PageStage.tsx`'s `.map()`).

*Alternative considered*: store decoded print-resolution images in the Zustand store (`ui` slice or a new slice). Rejected — this data is derived, ephemeral, and has no undo/redo or cross-component-tree relevance; a local hook with a module-scoped cache is simpler and keeps zundo's tracked/untracked state boundary (already a source of a real bug fixed earlier this project) out of the picture entirely.

## Risks / Trade-offs

- [Risk] No cache eviction — every distinct (image, target size) pair decoded during a session stays in memory until the app restarts. → Mitigation: bounded by the number of distinct images actually placed and previewed in one session (not, e.g., the whole Image Library or every possible zoom level, since preview has no manual zoom); acceptable for a first version, revisit if real usage shows it's a problem.
- [Risk] Large source images (the reported case includes a 5120×2880 photo) at 300 DPI print resolution for a large slot could still mean decoding and base64-encoding several megapixels per image, all at once when preview opens on a page with many large photos — a visible, if brief, delay before every image sharpens up. → Mitigation: the thumbnail-first progressive display (already a required scenario) means preview is never blocked or blank while this happens; if this proves too slow in practice, decoding could be triggered lazily per-page (only the currently-visible page's images) rather than for the whole document, which `PreviewStage`'s existing single-active-page architecture already naturally provides — no document-wide prefetch is being added.
- [Risk] `nativeImage.resize` on a very large source is a synchronous, CPU-bound call inside `ipcMain.handle` — a burst of several such calls (all images on a page) could briefly block Main's event loop. → Mitigation: out of scope to fully solve here (matches the existing `decodeAndThumbnail`'s same synchronous shape, an established pattern in this codebase); if it becomes a real stutter, a future change can move decoding to a worker thread — noted as a follow-up, not blocking this change.
