## Context

See `proposal.md` - Why/What Changes for motivation. Relevant current-state facts that shape the approach:

- `imageSlotConfig.focalPoint` (`{ x, y }`, normalized 0..1, default `{ 0.5, 0.5 }`) already exists in the schema (`packages/layout-engine/src/types.ts`) and `computeEnvelopeCrop` (`packages/layout-engine/src/imageFit.ts:19-49`) already accepts it as an optional third argument. No schema change is needed — this change is purely about letting the user set that field from the canvas, rendering it live, and making every consumer of `computeEnvelopeCrop` actually pass it through.
- **Nothing in the app passes `focalPoint` to `computeEnvelopeCrop` today, so it is entirely dead in practice** — found during implementation, not anticipated in the proposal:
  - The editor canvas's live preview (`src/components/canvas/SlotImage.tsx`) doesn't call `computeEnvelopeCrop` at all; it renders `envelopeParent` via plain CSS `object-fit: cover`, which always centers.
  - PDF/print composition *does* call `computeEnvelopeCrop` (`electron/main/pdf/composeProjectPdf.ts:65`, mirrored in `src/lib/android/composeProjectPdf.ts`), but only with two arguments (`spec.asset`, target aspect) — the third, `focalPoint`, is never passed, so it silently falls back to the function's own `{ 0.5, 0.5 }` default. `ImagePlacementSpec` (`electron/main/pdf/composeProjectPdf.helpers.ts`) doesn't even carry a `focalPoint` field to pass.
  - Both gaps have been invisible because nothing in the UI has ever set `focalPoint` away from center — but the second one is not just a cosmetic editor-only gap like the first. If left unfixed, panning would show correctly in the editor and print-preview (once `SlotImage.tsx` is fixed) but silently revert to a centered crop in the actual exported PDF or printed page, which would make the feature useless for its actual purpose. Both `pdf-export`'s and `printing`'s already-archived specs require output "rendered exactly as print preview renders it" — fixing this is what those existing requirements already call for, so it needs no new delta spec, just an implementation catching up to a standing requirement (same reasoning as the editor-canvas fix below).
- The slot-to-slot drag being removed is implemented as native HTML5 drag-and-drop (`src/hooks/useDragAndDrop.ts`, wired in `src/components/canvas/PageStage.tsx:357-361`), not the Pointer Events pattern the rest of `canvas-interaction` uses. It only applies to grid/flex `imageSlot` nodes rendered by `PageStage`; `FreeformElement.tsx` never wired it up, so freeform-canvas elements are already unaffected by its removal.
- The store's `source: 'page'` swap branch (`src/store/documentSlice.ts`, `assignImageToPage`) has exactly one caller — the `PageStage` wiring being removed — so it becomes dead code, not just an unused UI affordance.
- `canvas-interaction` already has an established Pointer Events + `setPointerCapture` convention for exactly this kind of gesture (divider resize, freeform move/resize/rotate, library image drag via `useLibraryImageDragGesture.ts`), and `undo-redo` already has a matching "batch a continuous drag into one undo step" pattern for two of those gestures (divider, freeform transform).

## Goals / Non-Goals

**Goals:**
- Let the user pan an `envelopeParent` slot's crop by dragging its image, reusing the existing `focalPoint` field end to end (canvas → store → layout-engine → PDF/print export all agree).
- Remove the slot-to-slot drag/swap feature completely (UI wiring, store branch, and its spec requirement), for every scaling rule.
- Keep the pan gesture consistent with this codebase's existing Pointer Events + single-undo-step conventions rather than inventing a new interaction pattern.

**Non-Goals:**
- Freeform-canvas elements are out of scope. Their shadow slot can also be `envelopeParent`, but the element's body already owns press-and-drag for moving the whole element (`canvas-interaction`'s "Freeform Element Move, Resize, and Rotate" requirement); layering a second, conflicting meaning onto the same gesture there is exactly the kind of incompatibility this change is removing elsewhere, not introducing. A future change can address panning inside a freeform element (e.g. via a modifier key or a dedicated handle) if wanted.
- No new UI control (button, double-tap-to-reset, numeric input) for `focalPoint` is added. The Properties panel is unaffected.
- No change to `computeEnvelopeCrop`'s math, clamping behavior, or the `focalPoint` schema itself.

## Decisions

**Reuse `focalPoint` directly; derive the pannable axis/range from `computeEnvelopeCrop`, not a new field.** The crop it computes already has exactly one axis where `cropWidth < asset.widthPx` or `cropHeight < asset.heightPx` (or neither, when the aspect ratios match) — that axis, expressed in on-screen render pixels via the slot's own rendered size, is both the pannable axis and the denominator for converting a pointer-pixel delta into a normalized `focalPoint` delta. This was confirmed as the right shape during proposal review: a float 0..1 per axis, gated by comparing the image's rendered size against the slot's size — which is precisely what the field and crop function already express, so no new state is introduced.

**Sign convention**: dragging the image to the right/down reveals more of the image's left/top (matches "grabbing the photo and sliding it," the common pan-to-reposition convention). Concretely, `focalPoint.x -= dxPx / overflowPx.x` (and symmetrically for `y`), where `overflowPx` is the rendered crop's overflow past the slot on that axis, clamped to `[0, 1]`.

**New gesture follows `useLibraryImageDragGesture.ts`'s Pointer Events pattern**, not the removed HTML5 DnD path: `onPointerDown` on the slot's `<img>`, `setPointerCapture`, `window`-level `pointermove`/`pointerup`/`pointercancel` listeners, `touch-action` tuned so the drag doesn't fight the page-preview panel's native scrolling on touch — the same concern already solved once for the Image Library card drag.

**Undo batching mirrors the divider/freeform pattern**: pause history recording on pointer-down (once the gesture is confirmed to be an `envelopeParent` slot), push live `focalPoint` patches through the existing `updateNodeById`-based patch path without recording intermediates, resume on pointer-up. If the drag never actually changed `focalPoint` (no overflow on either axis), no history entry is created at all, matching the "no-op drag creates no undo step" scenario.

**Remove the store's `source: 'page'` branch outright** rather than leaving it dead but reachable via the public `assignImageToSlot(pageId, nodeId, imageAssetId, source?)` signature — per this repo's no-backwards-compat-shims convention, an unreachable parameter value is deleted, not kept "just in case."

**`SlotImage.tsx` renders `envelopeParent` via an explicit position derived from `computeEnvelopeCrop`/`focalPoint`, instead of `object-fit: cover`.** The simplest option that stays consistent with the file's existing pattern (it already computes an explicit `renderRect` + `left`/`top` for `specificSize`) is to do the same for `envelopeParent`: compute the crop, size the `<img>` to the crop's on-screen (uncropped) rendered dimensions, and offset it by the focal-point-derived `left`/`top` inside an `overflow: hidden` slot box — replacing `objectFit: 'cover'` for this one scaling rule. `fitInParent`/`stretch` keep using `object-fit` as today.

**Thread `focalPoint` through the PDF/print composition path**: add `focalPoint: ImageSlotConfig['focalPoint']` to `ImagePlacementSpec` (`composeProjectPdf.helpers.ts`), populate it from `imageSlotConfig?.focalPoint` in `computePagePlacements` for both `imageSlot` and freeform-element placements, and pass `spec.focalPoint` as `computeEnvelopeCrop`'s third argument in both `embedPlacedImage` implementations (Electron and Android — they already share `ImagePlacementSpec`/`computePagePlacements`, so this is one shape change consumed identically by both). No change needed to `computeEnvelopeCrop` itself; it already accepts this argument.

## Risks / Trade-offs

- [Touch drag on a slot image could fight the page-preview panel's native scroll/pinch-zoom, the same problem `useLibraryImageDragGesture.ts` solved for the Image Library panel] → Mitigate the same way: only engage `setPointerCapture`/`preventDefault` once the gesture is confirmed as a pan (an `envelopeParent` slot with actual overflow), and tune `touch-action` on the slot image so unrelated touch gestures are unaffected. Verify on the Android build, not just desktop mouse, before calling this done — per this repo's UI-change testing expectation.
- [Removing slot-to-slot drag is a **BREAKING** change to existing muscle memory for anyone who used it] → Accepted per the user's explicit request; documented in the `project-persistence` delta's Migration note (two explicit assignments in place of one swap).
- [`SlotImage.tsx` is shared by the interactive editor canvas and the print-preview screen (`showDiagnostics` flag distinguishes them); its new `envelopeParent` rendering path must produce the same crop as `computeEnvelopeCrop`, for both `showDiagnostics: true` and `false`, and — now that PDF/print composition is also being fixed to honor `focalPoint` — the actual exported/printed pixels must match too, not just the two on-screen renderers] → All three consumers (editor canvas, print-preview, PDF/print composition) must agree at a non-default `focalPoint`; verify this directly (task 2.3) rather than assuming the shared `SlotImage.tsx` component and the separate `composeProjectPdf.ts` math stay in sync by construction — they're two independent implementations of the same crop math, not one shared function.
