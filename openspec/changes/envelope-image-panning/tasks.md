## 4. Undo/redo batching

- [x] 4.1 Pause history recording on pan gesture start (once confirmed to be an `envelopeParent` slot), matching the divider/freeform pattern already in the codebase — **found a pre-existing bug in that exact pattern while implementing this** (see note below) and used a corrected sequencing instead; flagged to the user rather than silently fixed elsewhere
- [x] 4.2 Resume history recording on pointer-up, collapsing the whole drag into one undo step — verified with a real `zundo` probe (see note) and covered by `src/store/index.test.ts`
- [x] 4.3 Confirm a drag that never changes `focalPoint` (no overflow) creates no undo entry — the hook only calls `onFocalPointChange`/pauses history when the computed value actually differs from the current one

**Pre-existing bug found, not fixed (out of scope for this change):** `NodeDivider`'s and `FreeformElementView`'s existing drags call `pauseHistory()` in `onDragStart`, *before* their first live update, then `resumeHistory()` in `onDragEnd` with no further store update after that. Empirically verified against the installed `zundo` version (`node_modules/zundo/dist/index.js`): `pause()` sets `isTracking: false`, and every `set()` call made while `isTracking` is `false` is skipped from history entirely — there is no retroactive capture of what changed during the paused span on `resume()`. A live probe calling the real `resizeSiblingsByDrag` action under that exact pause-then-resume sequence changed the document but added **zero** entries to `pastStates` (not one) — meaning divider-resize and freeform move/resize/rotate are likely not undoable as a single step today (or possibly not undoable at all), contradicting `undo-redo`'s own already-archived "Divider-Drag Gestures Batch Into a Single Undo Step" / "Freeform Element Transform Gestures Batch Into a Single Undo Step" requirements. This change's own pan gesture avoids the bug by pausing *after* the first tracked update instead of before it (see `useEnvelopeParentPanGesture.ts`'s doc comment), but does not touch `NodeDivider`/`FreeformElementView`'s existing (separate, pre-existing) wiring — that's a distinct fix the user should decide whether to make in its own change.
